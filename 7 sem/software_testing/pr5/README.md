# Практическая работа № 5 — OrderService, моки и параметризация

Работа по дисциплине «Технологии тестирования программных продуктов». Участники: Никитин Артемий, Ефремов Алексей, группа ЭФБО-10-23.

Сервис сохраняет заказ и при успехе отправляет уведомление. В тестах обе зависимости заменяются моками. Инструкция рассчитана на вашу **CachyOS Linux, x86_64**, с установленным **uv**.

## 1. Требования методички и их выполнение

Источник: [Практическая работа 5. Моки и параметризация](Практическая_работа_5_Моки_и_параметризация.pdf).

### Требования к сервису

| Требование | Реализация |
| --- | --- |
| Класс `OrderService(storage, notifier)` | Обе зависимости передаются в конструктор и сохраняются в объекте. |
| `place_order(order_id, data)` вызывает сохранение | Выполняется `storage.save_order(order_id, data)`. |
| Сохранение вернуло `True` | Вызывается `notifier.send(order_id, data)`, сервис возвращает `True`. |
| Сохранение вернуло `False` | Уведомление не отправляется, сервис возвращает `False`. |
| Хранилище выбросило исключение | Исходное исключение выходит наружу; уведомление не отправляется. |
| `get_order(order_id)` | Возвращает результат `storage.get_order(order_id)`: данные или `None`. |

Результат сохранения по контракту — булево значение. Реализация повторяет подход методички: проверяет его через `if saved`. Дополнительные правила валидации данных заказа не задаются.

### Обязательные проверки

| Требование | Где проверяется |
| --- | --- |
| Успех: результат `True`, одно уведомление с правильными аргументами | `test_place_order_success`: 3 набора данных. |
| Отказ: результат `False`, уведомления нет | `test_place_order_save_failed`. |
| Исключение при сохранении выходит наружу, уведомления нет | `test_place_order_storage_exception`: `Exception` и `RuntimeError`. |
| Получение существующего заказа | `test_get_order_existing`. |
| Получение отсутствующего заказа: `None` | `test_get_order_missing`. |
| Не менее 3 наборов успешного параметризованного `place_order` | Book — 500, Pen — 50, Laptop — 80000. |
| В релевантных тестах есть `assert_called_once_with` и `assert_not_called` | Проверяются вызовы хранилища и уведомлений во всех сценариях. |

Дополнительно проверяются порядок «сохранить → уведомить», передача именно исходного объекта исключения и отсутствие сохранения при чтении заказа. Каждый тестовый случай создаёт собственные моки и сервис.

**Итог текущей реализации:** 5 тестовых функций, 8 случаев с учётом параметризации, все 8 прошли. В отличие от Практики 4, методичка Практики 5 не задаёт минимум из 10 случаев, порог покрытия 90% и обязательные скриншоты. Для сдачи нужны код сервиса, тесты, вывод успешного прогона, комментарий о моках и взаимодействиях, ответы на 5 контрольных вопросов.

## 3. Как устроены моки и проверки

В каждом случае создаются:

```python
storage = Mock(spec_set=["save_order", "get_order"])
notifier = Mock(spec_set=["send"])
service = OrderService(storage, notifier)
```

`spec_set` ограничивает имена доступных атрибутов, помогая обнаружить опечатки в обращении к зависимости. Сигнатуры методов он здесь не проверяет; аргументы контролируются через утверждения о вызовах.

| Средство | Что делает в тестах |
| --- | --- |
| `return_value = True` | Моделирует успешное сохранение. Значение задаётся явно, поскольку обычный результат ненастроенного Mock сам является мок-объектом. |
| `return_value = False` | Моделирует обычный отказ сохранения. |
| `storage.get_order.return_value = data` | Задаёт существующий заказ без реального хранилища. |
| `storage.get_order.return_value = None` | Моделирует отсутствие заказа. |
| `side_effect = error` | Заставляет метод хранилища выбросить подготовленное исключение. |
| `assert_called_once_with(...)` | Проверяет ровно один вызов с указанными аргументами. |
| `assert_not_called()` | Проверяет отсутствие вызовов, например отправки уведомления при отказе. |
| `pytest.raises(...)` | Проверяет выход исключения из метода сервиса. |
| `caught.value is error` | Подтверждает, что наружу передан исходный объект исключения. |
| `attach_mock` и `mock_calls` | Объединяют историю двух зависимостей и позволяют проверить, что уведомление было после сохранения. |
| `pytest.mark.parametrize` | Запускает одну функцию на нескольких наборах данных как отдельные случаи. |

Сначала выполняется подготовка моков и данных (**Arrange**), затем вызов сервиса (**Act**), затем проверка результата и взаимодействий (**Assert**). Ошибки хранилища моделируются отдельно через `False` и исключение: это два разных пути исполнения.

## 4. Подготовка на CachyOS Linux

Используется Python **3.14.8** в локальной `.venv`, pytest **9.2.0** и установленный uv. Все команды ниже выполняются из каталога Практики 5.

```bash
cd "/home/aleksey/Documents/mirea_lab/7 sem/software_testing/pr5"
```

В текущей работе окружение уже создано. Проверить его можно так:

```bash
.venv/bin/python --version
uv pip list --python .venv/bin/python
```

Если подготавливаете окружение заново:

```bash
uv --version
uv venv --python /usr/bin/python3 .venv
uv pip install --python .venv/bin/python -r requirements.txt
```

При первоначальном получении Python и пакетов может потребоваться сеть. После установки тесты работают локально. Если `.venv` уже работает, создавать её повторно не нужно. Для повторной установки пакетов достаточно последней команды.

Активация окружения не требуется: команды обращаются к `.venv/bin/python` напрямую и подходят для запуска из Bash или Fish. Использование отдельного интерпретатора сохраняет проверенную версию Python независимо от системной.

## 5. Как запустить и повторить результат

### Полный набор

```bash
.venv/bin/python -m pytest test_order_service.py -v
```

Ожидаемый результат текущих исходников: **8 passed**. Каждый набор параметров отображается отдельной строкой.

### Сохранение вывода для сдачи

Следующая команда явно запускает Bash и сохраняет вывод через `tee`, показывая его одновременно в терминале:

```bash
bash -o pipefail -c '.venv/bin/python -m pytest test_order_service.py -v --color=no | tee pytest_output.txt'
```

| Часть команды | Назначение |
| --- | --- |
| `.venv/bin/python -m pytest` | Запускает pytest из окружения Практики 5. |
| `test_order_service.py` | Выбирает файл с тестами. |
| `-v` | Показывает название и результат каждого случая. |
| `--color=no` | Убирает цветовые управляющие последовательности из сохраняемого текста. |
| `tee pytest_output.txt` | Выводит текст в терминал и записывает его в файл, заменяя предыдущее содержимое. |
| `bash -o pipefail -c` | Выполняет конвейер в Bash и сохраняет ошибочный статус команды, если тесты завершились неуспешно, даже когда tee успешно записал файл. Работает и при вызове из Fish. |

`pytest_output.txt` — автоматически получаемый журнал запуска, его не нужно вручную переписывать. При повторении время и абсолютный путь в выводе могут отличаться.

## 7. Частые проблемы

| Ситуация | Что проверить |
| --- | --- |
| `No module named pytest` | Выполните `uv pip install --python .venv/bin/python -r requirements.txt`; запускайте тесты через тот же Python. |
| `No module named order_service` или тестовый файл не найден | Перейдите в `pr5`; `order_service.py` и `test_order_service.py` должны лежать рядом. |
| Не найдена `.venv/bin/python` | Создайте локальное окружение через `uv venv --python /usr/bin/python3 .venv` и установите зависимости. |
| Возник `AttributeError` у мока | Проверьте имя метода: storage допускает `save_order`, `get_order`, notifier — только `send`. |
| `Expected ... to be called once` | Проверьте число вызовов и их аргументы; сообщение pytest покажет расхождение. Не меняйте ожидание без сверки с методичкой. |
| При отказе тест сообщает о вызванном notifier | Убедитесь, что уведомление отправляется только после успешного сохранения и не находится до проверки результата. |
| Исключение не выходит наружу | Проверьте отсутствие перехвата ошибки в OrderService и правильность настройки `storage.save_order.side_effect`. |
| В журнале только часть тестов | Повторите полный запуск без выбора отдельной функции или набора параметров. |
| При запуске ничего не выводится | Запускайте pytest, а не `python order_service.py`: файл сервиса определяет класс, но не содержит самостоятельного сценария. |
