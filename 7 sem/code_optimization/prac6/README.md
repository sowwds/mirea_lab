## Что делает программа

Каждое задание проходит три этапа:

1. `stage_fetch` ждёт 0.03 с и создаёт 12000 чисел. Это имитация загрузки.
2. `stage_cpu` выполняет математические вычисления над числами.
3. `stage_post` обновляет состояние с учётом результата предыдущего задания.

Первые два этапа разных заданий независимы. Последний этап — цепочка: для следующего задания нужно уже рассчитанное состояние. Порядок менять нельзя. Ответ — `(состояние, число заданий)`.

Исходник `variant_9_baseline.py` оставлен без изменений. Новые модели находятся в `variant_9.py`.

## Четыре модели

| Функция | Как работает |
| --- | --- |
| `run_sequential` | Всё по очереди, эталон |
| `run_threads` | Четыре потока одновременно загружают и считают, состояние обновляется в основном потоке по порядку |
| `run_processes` | Четыре процесса загружают и считают, состояние обновляется в основном процессе по порядку |
| `run_async` | `asyncio` перекрывает ожидания; вычисления вынесены в пул из четырёх процессов через `run_in_executor` |

`pool.map` и `asyncio.gather` возвращают результаты в порядке заданий. Быстро закончившееся позднее задание не должно раньше попасть в `stage_post`.

GIL в используемой сборке Python не позволяет потокам одновременно выполнять вычисления Python. Потоки перекрывают ожидания, но вычисления конкурируют за GIL. У процессов отдельные интерпретаторы: они могут использовать разные ядра, зато их запуск и передача данных стоят времени.

`asyncio` само не ускоряет вычисления. Если вызвать тяжёлый расчёт прямо внутри корутины, он заблокирует цикл событий. Поэтому в решении используется `run_in_executor`.

## 5. Полный эксперимент

```bash
python benchmark.py
```

Это долгий запуск, он занимает несколько минут. Для защиты можно заранее выполнить его и показать графики и таблицы отчёта. Бенчмарк сначала прогревает все модели и измеряет этапы. Затем для каждого размера снова прогревает все модели и выполняет пять измерений каждой, чередуя их порядок. Прогрев не учитывается. Проверяются 1, 4, 16, 32, 64 задания.

В первой таблице — время загрузки, вычислений и обновления состояния, доли этапов и оценка Амдала. Во второй — медиана, диапазон min–max, ускорение S и эффективность E.

- `S = время эталона / время модели`. Если S меньше 1, стало медленнее.
- `E = S / p`, где p — число воркеров, здесь 4. Это условная эффективность относительно воркеров, основной процесс тоже выполняет служебную работу, а в модели процессов — ещё и `stage_post`.
- По Амдалу `S(p) ≤ 1 / (f + (1 − f) / p)`, где f — последовательная доля. В оценке берётся доля `stage_post`; это ориентир без расходов запуска и передачи данных. В конвейере `stage_post` может перекрываться с расчётами следующих заданий, поэтому подстановка всей его доли в f не даёт строгой границы для этой схемы.

Список номеров заданий создаётся до таймера. Создание чисел внутри `stage_fetch` остаётся частью исходного этапа и измеряется во всех версиях. Единицы работы не переписывались.

## Что объяснить про расходы

У процессов отдельная память. В `run_processes` в воркер передаётся номер задания, обратно — одно число. Большой список создаётся внутри воркера. В гибриде `asyncio` список создаётся в основном процессе и сериализуется для передачи в пул; это примерно 33 КБ на задание плюс служебные данные. После завершения всех расчётов `asyncio` запускает зависимые обновления состояния по очереди через executor.

Четыре процесса — умеренный выбор для восьми физических ядер. Дальнейшее увеличение не убирает зависимый `stage_post`, а расходы и конкуренция за ресурсы растут. Четыре потока достаточны для демонстрации перекрытия ожиданий; больше потоков не снимает GIL.

## Что сказать преподавателю

«Загрузку и независимые вычисления можно перекрывать. Обновление общего состояния зависит от предыдущего шага и сохраняет порядок. Потоки помогают ожиданиям, процессы позволяют параллелить вычисления, но требуют запуска и обмена данными. Для маленькой задачи пул невыгоден. Ускорение ограничено последовательным этапом».
