## Что сделано

Программа считает итоги продаж по дням и товарам. Исходник каждый раз заново перебирает продажи. В `variant_9.py` две версии кэша:

- `LruAnalytics`: готовый `functools.lru_cache`, максимум 32 итога. Любая запись очищает весь кэш.
- `ManualAnalytics`: `OrderedDict`, максимум 32 итога. Запись удаляет только итог затронутого дня и товара.

LRU означает «вытеснить то, к чему дольше всего не обращались». Инвалидация — удалить устаревший результат после изменения данных. Одного кэширования без инвалидации недостаточно: можно получить быстрый, но неправильный ответ.

Ключ — пара `("day", номер)` или `("product", номер)`, значение — рассчитанная сумма. Тип в ключе нужен, чтобы день 0 и товар 0 не путались.

## 3. Показать попадания в готовый LRU

```bash
python - <<'PY'
from variant_9 import LruAnalytics

an = LruAnalytics(10, 12)
print(an.daily_total(0))
print(an._cached.cache_info())
print(an.daily_total(0))
print(an._cached.cache_info())
an.update_sale(0, 0, 100)
print("После записи:", an._cached.cache_info())
print("Пересчитанный итог:", an.daily_total(0))
PY
```

Первое обращение: `misses=1`, второе: `hits=1`. После записи кэш очищен, статистика сброшена, следующий итог считается заново. Конкретные суммы здесь случайные; демонстрируется поведение кэша.

## 4. Показать точечную инвалидацию

```bash
python - <<'PY'
from variant_9 import ManualAnalytics

an = ManualAnalytics(10, 12)
an.daily_total(0)
an.daily_total(1)
an.product_total(2)
an.product_total(3)
print("До записи:", list(an._cache))
old = an.daily_total(0)
an.update_sale(0, 2, an.sales[(0, 2)] + 100)
print("После записи:", list(an._cache))
print("Сумма дня выросла на:", an.daily_total(0) - old)
PY
```

После записи остаются ключи дня 1 и товара 3. День 0 и товар 2 удалены. Сумма дня после пересчёта вырастет ровно на 100.

## 5. Показать вытеснение

```bash
python - <<'PY'
from variant_9 import ManualAnalytics

an = ManualAnalytics(10, 12, maxsize=2)
an.daily_total(0)
an.daily_total(1)
an.daily_total(0)
an.daily_total(2)
print(list(an._cache))
PY
```

Останутся `[('day', 0), ('day', 2)]`: день 0 недавно использовался, поэтому вытеснен день 1.

## 7. Показать время, память и бесполезный кэш

```bash
python benchmark.py
```

Появятся четыре таблицы:

- `original`: случайные отчёты на 40, 60 и 80 днях, затем повтор части отчётов;
- `hot`: всего 13 различных ключей — все помещаются в кэш;
- `updates`: те же часто используемые ключи, но продажи периодически меняются;
- `cold`: каждый ключ запрашивается один раз, кэш не помогает.

Время — медиана пяти запусков, создание продаж и запросов исключено. Память измеряется отдельным вызовом `tracemalloc` после создания продаж. Пик — максимум новых выделений Python во время запросов, «удержано» — оставшаяся после серии память, включая кэш. Это не вся память процесса.

## Что сказать преподавателю

«Сделаны две ограниченные стратегии. При обновлении продаж готовый LRU очищается полностью, ручной — только по двум зависимым ключам. При повторных запросах кэш ускоряет вычисления, при однократных тратит лишнюю память. Для повторов с обновлениями выбран ручной LRU».

Продажи меняем через `update_sale`, а не напрямую через `sales`: иначе инвалидация не сработает. В этой работе лимит — 32 записи, точный размер в байтах показывает измерение.
