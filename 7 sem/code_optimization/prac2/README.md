# Практика 2 — объяснение и показ

Вариант 9. Ефремов А. ЭФБО-10-23.

## Задача

Ускорить умножение двух квадратных целочисленных матриц одинакового размера, сохранив ответ. Для элемента результата используется формула:

```text
C[i,j] = A[i,0]·B[0,j] + A[i,1]·B[1,j] + ... + A[i,N−1]·B[N−1,j]
```

Например, первый элемент из задания: `1·9 + 2·6 + 3·3 = 30`.

## Что изменено

В `Program.cs` находятся обе реализации:

- `MultiplyMatricesOriginal` — исходный алгоритм для сравнения: циклы i → j → k.
- `MultiplyMatrices` — решение: циклы i → k → j; при A[i,k] = 0 внутренний цикл пропускается.

В исходнике B читается по столбцу: последовательные обращения далеко друг от друга в памяти. В решении B и результат читаются по строкам, что лучше использует кеш процессора. Элемент A[i,k] считывается один раз перед внутренним циклом.

Пропуск нулей корректен: `0·B[k,j] = 0`, ответ не изменится. Массив результата изначально заполнен нулями средствами C#.

Для плотных матриц обе версии имеют O(N³): перестановка циклов не уменьшает их число. Для разреженной A новый вариант имеет O(N² + Z·N), где Z — количество её ненулевых элементов. Если в каждой строке только два ненулевых элемента, Z = 2N, поэтому время — O(N²). Это улучшение зависит от данных, не общий квадратичный алгоритм умножения матриц.

```bash
dotnet run --project RPCApp9.csproj -c Release -- --check
```

Ожидается `Проверки пройдены: 107/107`.

Проверяются исходный пример с известным ответом, пустые матрицы, размер 1×1, нулевые матрицы, умножение на единичную матрицу, переполнение int и 100 случайных случаев с seed 42. Сравниваются все элементы ответов; для случайных случаев проверяется также сохранность входных матриц.

Это простые консольные проверки в том же проекте. Отдельного тестового фреймворка нет.

## 4. Показать ускорение

```bash
DOTNET_TieredCompilation=0 dotnet run --project RPCApp9.csproj -c Release -- --bench
```

Будут две таблицы на размерах 64, 128, 256, 384, 512:

1. Плотные матрицы — все элементы от 1 до 9.
2. Разреженная A — в каждой строке ровно два ненулевых элемента, B плотная.

В обеих версиях используются одни и те же матрицы. Генерация и проверка ответа не входят в замер. Перед измерениями два прогревочных вызова, затем пять повторений; берётся медиана. Время указано в миллисекундах с дробной частью.

`DOTNET_TieredCompilation=0` отключает переключение уровней JIT-компиляции на время этой команды: иначе код может перейти на другой уровень оптимизации посреди эксперимента. Это настройка измерений, а не изменение алгоритма. Release включает оптимизацию сборки.

Ускорение = время исходного алгоритма / время нового. Например, 100 / 50 = 2 раза. Конкретные времена зависят от нагрузки компьютера.

## 5. Что показать в редакторе

Открой `Program.cs` и сравни первые две функции. Покажи:

- вложенность i → j → k у исходника;
- вложенность i → k → j у решения;
- сохранение A[i,k] в factor;
- условие `if (factor == 0) continue`;
- внутренний цикл, который проходит по строке B[k,j] и результата C[i,j].

Можно временно поменять матрицу A в Main на нулевую и запустить обычный пример. Результат должен быть нулевой матрицей. После показа верни исходный пример. Аргументы терминала не задают матрицы: они только выбирают режим --check или --bench.

## Что сказать преподавателю

«Исходный алгоритм делает N³ умножений. Переставил циклы для последовательного доступа к строкам и пропустил нулевые коэффициенты. На плотных матрицах сложность остаётся кубической, но уменьшаются расходы доступа к памяти. При двух ненулевых элементах в строке выполняется 2N² умножений вместо N³.
