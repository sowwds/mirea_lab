## Что делает программа

Исходник `variant_9_baseline.py` обрабатывает одномерный сигнал в три этапа:

1. Применяет фильтр из пяти коэффициентов: для каждого окна считается взвешенная сумма.
2. Нормализует результат в диапазон 0…1. Для постоянного сигнала получает нули.
3. Для каждого i берёт следующие максимум 29 элементов и записывает пары признаков: `normed[i] − normed[j]`, затем `normed[i] · filtered[j]`.

Ответ — три полных массива: filtered, normed, feats. Их порядок сохраняется во всех версиях. Для TINY=8 после фильтра остаётся 4 значения и 12 чисел признаков.

При постоянных длине фильтра 5 и WINDOW=30 время O(N). Число пар линейно растёт с размером сигнала. Не нужно строить матрицу всех N² пар.

## Какие версии сделаны

| Функция | Реализация |
| --- | --- |
| `run_baseline` | Исходные циклы Python |
| `run_numpy` | Фильтр через np.correlate, нормализация массивными операциями, признаки через представление окон и broadcasting |
| `run_numba` | Циклы с @njit, без fastmath |
| `run_parallel` | Numba, независимые строки признаков через prange, 4 потока |
| `run_processes` | Фильтр и нормализация в основном процессе; признаки считаются порциями в четырёх процессах |

В prange каждая строка пишет в свой участок результата. Общего счётчика записи нет: начало участка вычисляется из номера строки. Поэтому гонки за данные отсутствуют. Нормализация и фильтрация остаются последовательными в этой версии.

У процессов порция включает до 29 соседей за своей правой границей, чтобы последние строки порции не потеряли признаки. Соседние данные могут повторно передаваться, но каждая строка результата вычисляется ровно один раз. pool.map сохраняет порядок порций.

## 4. Показать cold и warm

```bash
python - <<'PY'
from time import perf_counter
from variant_9_baseline import make_workload
from variant_9 import prepare, run_numba

arrays = prepare(make_workload(16000))
for label in ["Первый вызов", "Повторный", "Ещё один"]:

```

Cold включает получение машинного кода при первом вызове. Warm использует уже готовый код. Здесь данные заранее преобразованы в ndarray, поэтому это показ режима «ядро».

## 6. Полный эксперимент

```bash
python benchmark.py
```

Запуск занимает несколько минут. Сначала проверяется измеритель памяти: выделение и заполнение массива на 64 МиБ должно увеличить текущую RSS хотя бы на 48 МиБ. Затем выводятся cold/warm и таблицы на шести размерах: TINY=8 и все пять значений SIZES.

- **Ядро:** данные уже лежат в непрерывных массивах float64.
- **E2E:** исходные списки превращаются в массивы внутри измеряемого вызова.
- Python и процессы работают с исходными списками, поэтому у них ядро и E2E — один и тот же замер.
- Время — медиана пяти повторов, рядом min–max. Быстрые функции вызываются многократно в каждом повторе. Прогрев и генерация сигнала в замер времени не входят.
- S — время Python / время выбранной версии.
- Для prange отдельно выводятся S относительно однопоточной Numba и E = S / 4.

Повторить только измерение памяти:

```bash
python benchmark.py --memory-only
```

Память измеряется в отдельных свежих процессах внешним счётчиком текущей RSS с шагом 5 мс. Включены интерпретатор, библиотеки, входы и результаты; для Numba также прогрев с JIT-компиляцией. ## Короткие ответы на контрольные вопросы

1. **Почему Python медленнее?** Интерпретирует каждую итерацию, выполняет динамические операции над объектами, создаёт результаты Python. NumPy выполняет циклы в скомпилированном коде над плотным числовым буфером, Numba компилирует сами циклы.
2. **Что происходит при первом @njit?** Определяются типы, строится и оптимизируется машинный код. Это cold. Вызовы с теми же типами используют готовую специализацию — warm.
3. **Когда prange корректен?** Когда итерации независимы или используется допустимая редукция. Общий изменяемый индекс записи дал бы гонку. У нас диапазоны записи не пересекаются; параллельного суммирования нет.
4. **Почему NumPy требует больше памяти?** Broadcasting создаёт временный массив разностей или произведений размера примерно N×29. sliding_window_view сам данные не копирует, но результат операции над этим представлением занимает память.
5. **Что такое порог окупаемости N*?** Размер, начиная с которого выбранный подход быстрее baseline при зафиксированных условиях. Его ищут замерами и уточнением размеров между соседними точками. Для NumPy warm переход в этом эксперименте находится между 8 и 16000; точное значение не измерялось. Cold имеет другой порог.
6. **Почему процессы часто проигрывают?** Сохраняют вычисления над объектами Python и добавляют отдельные интерпретаторы, передачу данных и объединение результатов. Нужны для крупных независимых задач, которые нельзя эффективно выразить через NumPy или Numba, особенно при малом объёме пересылки.
7. **Зачем допуск?** Порядок и способ сложения float могут немного отличаться, в том числе у Python 3.14, NumPy и Numba. Используется проверка |a−b| ≤ atol + rtol·|b|, здесь atol=1e-12, rtol=1e-11. Вблизи нуля важен atol. Повторные вызовы одной версии проверяются строго.
8. **Что даёт fastmath?** Позволяет переставлять и упрощать вычисления с float, что может изменить результат и работу с NaN/inf. В решении fastmath не включён. Поддерживаемый набор входов — конечные вещественные значения, подготовленные как одномерные float64-массивы.
